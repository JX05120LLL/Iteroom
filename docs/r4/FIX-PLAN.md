# R4-3：关联修复与新快照复查实施计划

**目标**：用户选择已定位候选后创建有来源的 R2 修改任务；R3 接受后显式固定新的工作树审查输入，旧报告不充当修复证据。

**依据**：[PRD 4.3](../PRD.md)、[R4 计划](PLAN.md)与已确认的 README 流程。按用户继续开发授权，在当前工作区顺序实施，保留已有改动，不 commit/push，不另建第二套 Loop。

**架构**：新增 `ManagedReviewFix` 协调现有 Store、快照、准备和结果模块。修改任务原子保存 `reviewOrigin`（reviewTaskId/preparationId/reportId/findingId/path/sourceSha256），复查任务保存 `recheckOrigin`（modifyTaskId/artifactId）；仍为 v1 可选字段，旧记录可读。运行、沙箱、接受、模型预算沿用 R2/R3/R4-2。

## 接口与边界

- `POST .../review/fix` 精确 `{taskId,findingId,requestId,objective,testPaths}`：只接受完成报告中已定位的 new 侧 modified 普通源文件；拒绝旧侧、删除、重命名和常见 `.test/.spec` 或 test/tests/__tests__ 目录内的测试目标。目标整文件必须仍匹配发现的源码 Hash。用户显式选择 1–15 个固定 `.test.js/.test.mjs/.test.cjs` 文件；沿用路径/编码/大小检查。只登记和固定输入，不发模型、执行命令或写源码。
- `POST .../review/recheck` 精确 `{taskId,requestId}`，taskId 是已接受的关联 modify。核对产物、接受记录及当前文件 Hash；调用现有真实 OCR 准备新工作树输入。原问题目标必须仍在新变更范围内且新侧等于已接受结果；恢复为无变更文件暂明确拒绝，不以 no_changes 冒充复查通过。准备不启动模型，用户另行开始审查。
- 请求去重包含关系和全部用户输入；同请求并发合并，重启返回已有固定任务。不同内容复用 requestId 拒绝，不重放模型。准备失败不允许未经固定校验的修改启动。
- 关联记录依赖现存父任务；存在修复/复查子记录时阻止父历史删除，先删除子记录。单 Host 占用及磁盘锁沿用原边界，不声称多 Host 原子流程。
- UI 保留白色方案 C。审查页选择发现、填写修复目标/测试范围、创建后打开修改页；修改页展示来源，接受后提供固定新输入复查动作，创建后打开审查页。模型、执行、接受保持分开的显式动作。
