# Iteroom 产品需求文档

> 版本：0.1（产品规划稿）
> 日期：2026-09-23
> 状态：M0 已加入 DSH Web 上的 UI 审核版；文字任务闭环、实时语音和发行验收仍待完成
> 旧项目：D:\code\RepoPilot 是独立仓库，迁移范围须逐项评估

## 1. 产品决策摘要

**产品定位：** Iteroom 是面向个人开发者的开源、本地优先编程助手。用户从一个代码仓库启动本地 Web 页面，与助手讨论代码、提出修改要求、观察执行过程，并审阅 Diff 与验证结果。首版以文字交互完成闭环；后续逐步加入实时语音、个性化记忆、经验检索和经评测的策略改进。

**首版交付形态：** 发布 npm 包后，目标体验是在项目目录执行一条命令，例如下方的目标命令，自动启动本机服务并打开页面。这是发布目标，目前尚未实现或发布：

~~~sh
npx iteroom .
~~~

**用户承诺：** 能看见助手在当前项目中读了什么、改了什么、验证了什么；无法验证时明确说明。用户能够停止进行中的任务并继续已有会话。

**产品特色：** 代码位置与对话绑定；文字版与未来语音版共用同一任务状态；修改结果与验证证据相互关联；偏好和经验可以溯源、纠正；自动改进必须通过独立评测后才能启用。

**首版非目标：** 多用户、登录、云端托管、实时语音、LightRAG 索引、自动生成长期记忆、自动修改 Harness 核心代码、无人值守提交或推送。

## 2. 用户与问题

首要用户是使用本地 Git 仓库的个人开发者，包括学生和独立开发者。用户会提出“解释这段代码”“定位错误”“修改实现并运行相关测试”等任务，希望快速开始，并能理解助手的操作及结果。

现有 RepoPilot 已实现过审计、验证和项目工作区等能力，但运行形态包含 Python 后端与 Tauri 桌面端。本项目重新定义发行形态和产品范围；旧项目的代码只能在逐项检查许可证、接口、依赖和维护成本后迁入。

| 场景 | 用户动作 | 必须看到的结果 |
|---|---|---|
| 理解代码 | 在当前项目提问，或选择文件/代码范围后提问 | 回答引用可打开的文件与位置；不发生写入 |
| 修改代码 | 提出一个可描述的小改动 | 工具执行状态、实际 Diff、改动文件 |
| 验证改动 | 要求运行项目测试或构建 | 执行命令、范围、退出码、测试摘要与未知点 |
| 中途干预 | 输入追加要求或点击停止 | 追加内容进入正确会话；停止后显示最终状态 |
| 跨次使用 | 重新打开项目与会话 | 能查看历史和继续对话，状态不重复执行 |

## 3. v0.1：文字版最小完整产品

### 3.1 首次使用流程

1. 用户安装满足发布包要求的 Node.js 与 npm，在仓库目录运行 Iteroom 命令。
2. 启动器检查运行环境，选择可用端口，绑定本机回环地址，启动 Web 服务并尝试打开浏览器；自动打开失败时打印可访问地址。
3. 首次页面引导用户配置模型提供方与凭证，并说明代码内容会按所选模型服务的方式处理。凭证存放在本机配置区域，不写入当前代码仓库。
4. 项目默认为命令执行目录。用户可以在界面中确认或切换项目；界面展示明确的工作区边界。
5. 用户发起文字任务，实时看到回复、工具活动和任务状态。
6. 任务完成后，用户查看 Diff、验证证据与未验证项，再继续追问或结束。

首次下载 npm 包、首次安装依赖、首次模型配置可以增加准备时间。“一条命令”指启动入口简单，不承诺无网络、无模型配置或目标项目无需自己的构建工具链。

### 3.2 功能与验收

| ID | 能力 | v0.1 验收标准 |
|---|---|---|
| P0-01 | 本地启动 | 从发布包或待发布 tarball 启动，无需克隆源码、手工编译前端、另启 Python/Tauri/Docker 服务；退出后服务与子进程可收束 |
| P0-02 | 项目绑定 | 展示当前工作目录；所有代码操作归属明确项目；路径访问由运行时策略检查 |
| P0-03 | 文字会话 | 发送消息、看到流式内容与工具状态；刷新或重启后可恢复已持久化会话 |
| P0-04 | 代码定位 | 文件引用可打开；用户选中的文件或代码范围可以随本次任务传给助手 |
| P0-05 | 修改审阅 | 显示文件级 Diff 与改动摘要；原有未提交改动得到识别，不能被误报为本次任务产物 |
| P0-06 | 验证结果 | 记录实际命令、目标范围、退出状态与可取得的测试摘要；未运行或证据不足显示“未验证” |
| P0-07 | 任务控制 | 用户可以追加要求、停止任务；界面区分运行中、等待输入、完成、失败、取消中和已取消 |
| P0-08 | 配置与恢复 | 模型配置错误、端口占用、运行时失败有可执行的提示；恢复后不重复提交同一条用户消息 |
| P0-09 | 本机访问 | 默认只绑定回环地址；本地 API 保持浏览器访问所需的来源与会话校验 |
| P0-10 | 开源交付 | README、快速开始、支持平台、数据流向、许可证与第三方归属清楚；干净环境可复验一次完整任务 |

“验证通过”只描述实际执行的检查范围，不等于全部业务正确。停止任务也不意味着撤销已经写入的文件；界面必须让用户看见取消前留下的改动。

### 3.3 页面与交互

v0.1 至少需要首次配置页、项目与会话入口、主工作区、Diff/验证结果视图。主工作区要让用户同时看到“正在讨论什么代码”“助手目前做什么”“修改与验证结果在哪里”。窄屏可以折叠面板，但任务状态始终可见。

本轮复用 DSH Web 的现成页面框架，做可点击的品牌与语音界面审核版。视觉方向已选定[方案 C](design-options/README.md)：工作台与独立通话页以白色为主背景，使用双拱门 Logo；通话页保持简洁单栏。设计稿中的会话、文件和字幕只是示例，运行界面必须展示真实会话状态。该选择只确定 M0 的视觉基线，不等于本节全部页面和交互已完成。后续仍需补齐用户流程与状态图、首次配置和审阅视图，并在真实浏览器检查空项目、无模型、等待工具许可、工具失败、会话重连和任务停止。

## 4. 架构与复用边界

DeepSeek Harness 使用 Cordis 插件树组装模型、工具、会话与 Agent Loop；Web 是官方支持的运行 Profile。Iteroom 首先验证官方 Web Profile 和扩展点能否承载产品交互，再固定已验证的上游版本与接入接口。[DSH 架构](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md)、[CLI 入口](https://github.com/deepseek-ai/deepseek-harness/blob/master/apps/cli/README.md)

| 能力 | 复用边界 | Iteroom 自己负责 | 尚需验证 |
|---|---|---|---|
| 模型请求、工具循环、流式响应 | DSH 模型适配与 Agent Loop | 产品任务入口和展示 | 模型路由、取消、错误恢复 |
| Session、会话恢复、上下文压缩 | DSH 会话与持久化插件 | 项目与会话入口、产品状态映射 | 重启后数据一致性、格式迁移 |
| 读写文件、Shell、Skill、MCP | DSH 能力及策略接口 | 默认能力组合、产品说明与审阅体验 | 当前 Profile 的实际能力和许可行为 |
| 工具与代码改动展示 | DSH 事件、现有可用 UI 组件 | 面向项目的 Diff、验证证据与状态归类 | 能否从稳定接口获得所需事件与文件状态 |
| 本地 Web Host | UI 审核版已依赖固定版本的 DSH Web Profile 和现有布局、侧栏、文字会话组件 | npm 启动器、配置引导、品牌与产品 UI | 完整会话控制、权限边界、发行和升级成本 |
| 个人偏好、语音、经验检索、自动改进 | 分阶段复用 DSH、LiveKit、LightRAG 相应能力 | 记忆规则、交互协调、评测与版本管理 | 每阶段单独做技术验证 |
| 旧 RepoPilot | 已有任务、验证、证据设计可参考 | 逐项判断迁移价值 | 不直接搬运旧 Python 编排或依赖树 |

**接入方案验证：** 当前 UI 审核版已用 DSH Web Profile 配合 Iteroom 浏览器插件扩展品牌、输入区和主视图，未复制上游前端或另建 Agent Loop。项目入口、状态展示和审阅操作是否满足 M1，仍需端到端演示；若 UI 自由度不足，再比较“独立 Web 界面 + DSH Host/API Gateway”方案。取消、重连、权限、版本升级都尚未由此 UI 审核版验证；不能把当前较窄的 SDK 协议假定为完整的 Web 产品接口。[DSH SDK 协议](https://github.com/deepseek-ai/deepseek-harness/blob/master/packages/sdk/protocol/README.md)

**避免双重状态：** DSH 的 Session 是对话与 Agent 执行历史的权威来源。Iteroom 只保存产品需要的项目选择、验证索引、偏好与策略版本，并以明确标识关联到对应 Session、任务和代码快照。

### 4.1 当前 UI 审核版

- **已加入的界面：** 通过 `iteroom.patch.yml` 在固定的 DSH Web Profile 上装载 Iteroom 插件，使用 DSH 已有的页面布局、侧栏和文字会话界面；按方案 C 换上白色主题、深绿色语义色与双拱门 Logo，在文字输入区添加语音按钮、在侧栏添加“语音空间”入口，并提供独立的白底通话页。
- **状态与交互：** 通话页提供返回当前文字会话的入口，显示“尚未连接”和空字幕状态，不放设计稿中的示例任务或示例字幕。语音按钮只负责导航；麦克风、字幕和结束通话控件禁用，不请求浏览器麦克风权限。文字会话入口仍由 DSH 提供，尚未宣称符合 P0-01 至 P0-10。
- **接口边界：** 当前插件只使用 DSH 的 UI Slot 与布局切换能力；尚未定义音频流、转写、打断和代码任务状态之间的接口，也没有接入 LiveKit。M2 需在同一 Session 与任务状态上完成真实语音闭环。
- **验收范围：** 本机 Windows / Node.js 24.14.0 上已构建并启动固定版本 DSH Web；Chromium 中检查了品牌显示、侧栏与输入区语音入口、通话页返回、桌面及 390×844 手机布局。浅色和深色偏好下页面与侧栏均保持白底；手机通话页无横向溢出。方案 C 的白色品牌皮肤覆盖 DSH 深色外观选择。该结果只覆盖 UI 审核版；DSH 升级兼容、真实模型任务、权限、语音和发行均未验证。部分视觉覆盖依赖当前固定 DSH 版本的 CSS 类名，升级时需复测；DSH 的内测声明、模型配置提示和部分首页文案仍沿用上游。

### 4.2 本地发行目标

发布包提供一个 npm 可执行入口；前端产物和所需 DSH 运行时随受测版本打包。启动器负责选择端口、准备本地配置、启动 Host、打开浏览器与接收退出信号。用户数据放在独立的本机数据目录，不默认写入目标仓库。

M0 必须通过 npm tarball 在干净环境测试 Windows；其他系统在实际复验后才列入支持范围。要分别记录“首次下载至可用”和“已有依赖的再次启动”耗时。支持的 Node 版本由所选 DSH 版本及实测结果确定。开发者的源码启动流程与终端用户的一条命令流程分别文档化。

## 5. 分阶段演化

每阶段都建立可以独立演示、回归和交付的用户闭环。下一阶段以已完成阶段的稳定版本为起点。

| 阶段 | 交付范围 | 完成判据 |
|---|---|---|
| M0：接入与发行试验 | 固定 DSH 版本，验证 Web 扩展或 Host 接入；从 npm tarball 启动页面并完成一次模型、工具、取消事件流。当前仅加入 UI 审核版 | 写出接入决策与实测限制；安装包在目标平台的干净环境启动 |
| M1：文字首版 | P0-01 至 P0-10；代码讨论、修改、验证、Diff 审阅、会话恢复 | 三类真实任务可演示；项目外范围、取消、重启和失败路径有验收记录；首个可公开使用的发布候选 |
| M2：实时语音协作 | LiveKit 驱动语音输入、字幕、播报与用户打断；当前代码选择随语音指令传递 | 用户说话停止播报；“停止任务”才触发代码任务取消；耗时任务可接收补充指令并播报真实状态 |
| M3：个人风格记忆 | 明确表达的交流与开发偏好可保存、查看、修改、删除 | 换会话仍按已确认偏好交流；一次临时要求不会自动变成永久偏好 |
| M4：项目经验检索 | 按需接入 LightRAG，索引适合长期保存的决策和经验 | 检索带来源、项目范围与版本；与无检索基线比较效果和延迟 |
| M5：可评测的持续改进 | 从失败和反馈提出候选 Skill 或策略，在独立任务集评估后启用 | 保留旧版本、拒绝退化、支持回滚；报告收益、耗时和成本 |

M2 的语音接入不以“听到人声就取消代码任务”为规则：停止朗读、补充要求和停止任务是三种不同动作。LiveKit 负责实时媒体与打断基础；DSH 继续负责代码任务，Iteroom 负责两者的状态映射。[LiveKit 轮次与打断](https://docs.livekit.io/agents/logic/turns/tuning/)

M3 的简单偏好优先采用可编辑的结构化存储。M4 在确实需要跨文档、跨任务关系检索时再接入 LightRAG；不能让每轮语音响应都等待图谱检索。[LightRAG 官方仓库](https://github.com/HKUDS/LightRAG)

M5 的学习环为：执行 → 记录失败及反馈 → 提出候选策略 → 在独立任务上比较 → 启用或保留旧版 → 观察退化并回滚。进行中的任务固定策略版本。评测数据、验收器和权限策略不由待评候选自动改写。

## 6. 质量、指标与验收证据

v0.1 记录：启动成功率、首次准备和再次启动耗时、项目任务成功率、错误宣告验证通过的次数、用户停止到执行停止的耗时，以及失败恢复情况。发布说明只报告实际测过的平台、项目类型、模型与测试范围。

M2 增加：识别准确性、用户说话至播报停止、说完至首次有意义回答、语音补充指令至 Agent 采纳的延迟；统计中位数和较慢请求的分布。M3/M4 增加偏好误用率、经验检索命中率与延迟。M5 使用固定基线和独立留出任务集比较策略版本，并记录成本。

每次演示至少保留一个完整记录：任务输入、项目与版本、实际改动、执行过的验证、结果及未验证项。模型口头称“成功”不构成验收。

## 7. 数据、权限与开源边界

- 默认本机单用户、本机回环地址；不引入账号系统。由于页面可以发起本机代码和命令操作，Host 必须维持来源校验、会话边界与工具策略。
- 首次配置清楚展示模型服务与数据流向。API 密钥不写入项目文件或 Git，不出现在诊断导出里。
- Session、偏好、经验记录提供查看和删除入口；M2 默认不把原始音频写入长期记忆。
- 项目权限和风险操作由 DSH 运行时及产品接入层共同验证；Skill、记忆和检索结果不能直接改变工具权限。
- 发布前核对依赖许可证及归属。当前 DSH 根许可证为 MIT，复制其源码或实质内容时应保留适用的版权和许可文本；其他依赖分别核对。[DSH LICENSE](https://github.com/deepseek-ai/deepseek-harness/blob/master/LICENSE)
- 本仓库当前没有选定最终许可证；在公开发布前确定并补齐 LICENSE、第三方声明和贡献说明。

## 8. 风险与决策门槛

| 风险 | 何时解决 | 必须取得的证据 |
|---|---|---|
| DSH Web UI 扩展不足或接口变化 | M0 | 同一 PoC 中跑通提交、流式事件、停止、恢复和 Diff 入口 |
| npm 包隐含 Python、Tauri、手工构建步骤 | M0 | 干净环境安装与启动记录 |
| 首版通用性被理解为所有语言都已测试 | M1 | 按语言与构建工具列出真实测试矩阵 |
| 浏览器页面对本地代码工具的访问边界 | M0/M1 | 回环地址、来源校验、权限与路径测试 |
| 音频交互拖慢编码任务或重复提交 | M2 | 打断、误触发、断线重连、长任务补充指令的实测 |
| 错误记忆越积越多 | M3/M4 | 来源、范围、过期、编辑和删除路径 |
| 自优化只在旧题上变好 | M5 | 独立测试集、旧版对照、退化拒绝与回滚演示 |

## 9. 开发与开源交付流程

当前从 DSH Web 界面复用出 M0 UI 审核版，方案 C 已选为视觉基线。之后完成 M0 的接入与发行验证、M1 的用户流程原型和文字闭环，再逐阶段实现。每个阶段以具体行为和验证命令给 Codex 下任务；Codex 同步更新 PRD、架构决策、UI 状态和里程碑记录。一次改动若改变产品边界，应同步修改相应文档。

首个公开发布的完成条件：陌生开发者根据 README 在声明支持的平台启动 Iteroom，完成一次文字代码任务，查看真实 Diff 和验证证据，并知道出现失败或无法验证时该怎么处理。GitHub 仓库与 npm 包在实际发布后分别验证可访问和可运行；本规划稿及本地 Git 仓库本身不等于发布完成。

## 10. 命名

项目名：**Iteroom**，由 iterate（迭代）与 room（工作空间）组合而来，强调开发者与助手在同一空间持续讨论、修改和验证代码。技术标识暂定为 Git 仓库目录 Iteroom、npm 包与命令 iteroom。GitHub 私有仓库已创建；npm 包尚未发布。名称与包名在正式公开发布前仍需核查。
